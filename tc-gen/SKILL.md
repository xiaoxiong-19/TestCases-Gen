# tc-gen：新需求测试用例生成

为项目新需求生成高质量测试概要与测试用例。**分 5 个阶段，每个阶段产出后必须停下来等用户确认/纠正，禁止一次性走完。**

本技能以**本地需求文档 + 本地代码知识库（`.dev-standards`）**为主；`user-dev-standards` MCP 为**可选增强**（可用于知识发现、需求校验和交叉验证），**不强制调用**。若 MCP 不可用、调不通、超时或无匹配结果：**记录一次原因后立即 fail-open 回退本地流程，禁止重试/等待/卡死**；若未使用 MCP，也无需强行补调。

## 核心原则

- **需求文档只写「增量」，代码知识库（`.dev-standards`）写「全量」。** 有知识库时必须结合两者：既测新功能，又不漏被影响的老功能。
- **本地知识库优先，MCP 可选。** 不强制读取/调用 MCP。若 MCP 可用且用户环境已配置，可选用它辅助定位业务规则、需求疑点和服务知识；最终仍以本地业务文档、代码地图、流程定义和接口文档全文为准。
- **接地气且可追溯。** 所有测试点必须有证据链：需求变更项、业务文档章节、状态机/配置矩阵/通知矩阵、接口字段、代码地图 Handler/风险点；若使用了 MCP，可补充 MCP 业务规则来源。禁止编造泛泛用例。
- **人工卡点。** 每阶段结束输出「请确认是否继续」，等用户回复后再进入下一阶段。
- **版本隔离。** 每个迭代版本独立放在 `.test-standards/<版本>/` 下；`.test-standards` 根目录只初始化一次，不在根目录直接放 `input/output`。
- **严禁以活源码替代知识库。** `codemap`/业务文档/`procdefs` 均指代码知识库（默认路径 `.dev-standards`）下预先沉淀的**静态文档**，不是项目活源码。测试用例的依据是「系统应该做什么」（需求文档 + 接口规范），不是「系统现在写了什么」（活源码）。原因：① 同步开发的新功能代码在开发人员本机，远程仓库尚未有最新提交，读到的是不完整的早期骨架；② 用代码反推测试用例本质上是「以代码校验代码」，无法发现实现偏差。

## 调用方式与初始化规则

当用户说类似 `tc-gen初始化版本“V1.12.0-xxx”`、`tc-gen 初始化版本 V1.12.0-xxx` 时，执行初始化，不进入阶段0。

### 脚本路径约定

- **不要写死** `.cursor/skills/...` 或其他 IDE 私有路径。
- `tc-gen` 内置脚本路径一律相对于**本 skill 安装目录**（即包含本 `SKILL.md` 的目录），记作 `<本skill目录>`。
  - 示例：若技能装在当前软件 skills 下的 `tc-gen/`，则执行
    `python "<本skill目录>/scripts/init_version_utf8.py" ...`
  - Agent 运行前须把 `<本skill目录>` 解析为加载本 skill 时的真实绝对路径。
- 跨 skill 脚本（如 `tc-convert`）相对于**当前软件的 skills 根目录**，记作 `<当前软件skills目录>`。
  - 以实际加载本 skill 的软件为准（例如 Cursor 的 skills 根、Trae 的 skills 根），不要写死某一产品目录名。
  - Agent 执行前须解析为绝对路径。
- 下文命令中的 `"<本skill目录>/scripts/..."` / `"<当前软件skills目录>/..."` 仅为占位符。

初始化规则：

1. 在代码项目根目录下检查 `.test-standards`。
2. 如果 `.test-standards` 不存在，则创建；如果已存在，不重复初始化根目录，不覆盖其中已有文件。
3. 初始化版本目录时，必须使用本 skill 内置 UTF-8 脚本，禁止用 PowerShell/cmd 直接 `mkdir` 或 `New-Item` 创建含中文版本目录：

```bash
python "<本skill目录>/scripts/init_version_utf8.py" "<项目根目录>" "<版本>"
```

4. 如果 `<版本>` 包含中文、空格或 shell 中显示乱码，先把版本名写入 UTF-8 文本文件首行，再使用 `--version-file`，避免 Windows GBK/CP936 终端把中文参数解码错误：

```bash
python "<本skill目录>/scripts/init_version_utf8.py" "<项目根目录>" --version-file "<UTF-8版本名文件>"
```

5. 脚本会在 `.test-standards` 下创建版本目录：`.test-standards/<版本>/`。
6. 在版本目录下创建：

```text
.test-standards/<版本>/
├── input/
│   ├── prodword/      # 需求文档目录，沿用原 requirement 逻辑
│   │   └── prodword_pic/  # 需求文档图片目录，Word 转 md 时同步抽取图片
│   └── reference/     # 三方接口文档/联动参考资料，沿用原 reference 逻辑
└── output/            # 阶段产物目录，沿用原 output 逻辑
```

7. 如果版本目录已存在，只补齐缺失子目录，不删除、不覆盖已有输入或输出。
8. 初始化完成后，提示用户把需求文档放到 `input/prodword/`，把接口/三方/联动资料放到 `input/reference/`。`input/prodword/prodword_pic/` 由转换流程存放需求文档图片，用户也可手动补充流程图原图。
9. `.test-standards` 根目录下不得直接创建版本无关的 `input/` 或 `output/`。

### 初始化编码要求

- 所有版本目录初始化必须走 `tc-gen/scripts/init_version_utf8.py`。
- 含中文版本名时优先使用 `--version-file`，版本名文件必须以 UTF-8 或 UTF-8 with BOM 保存。
- 初始化脚本只创建目录，不覆盖已有输入文件和阶段产物。
- Agent 不得用 shell 内嵌中文命令创建版本目录，例如 `mkdir ".test-standards/V1.0.0-支付宝"`、`New-Item`、`python -c "..."`。

### 版本输入发现要求

- 阶段0开始前，必须先运行本 skill 内置 UTF-8 脚本发现版本目录和输入文件，禁止用 `Glob` 直接扫描 `.test-standards/<中文版本>/`：

```bash
python "<本skill目录>/scripts/list_version_inputs_utf8.py" "<项目根目录>" "<版本>"
```

- 如果 `<版本>` 含中文、空格或 shell 中显示乱码，优先使用 `--version-file`；如果只有前缀是 ASCII 且能唯一匹配，也可以用 `--version-prefix`：

```bash
python "<本skill目录>/scripts/list_version_inputs_utf8.py" "<项目根目录>" --version-file "<UTF-8版本名文件>"
python "<本skill目录>/scripts/list_version_inputs_utf8.py" "<项目根目录>" --version-prefix "V1.0.0-saas"
```

- 脚本输出 JSON，包含 `versionRoot`、`input/prodword`、`prodword_pic`、`input/reference`、`output` 的存在性和文件清单。后续读取、转换、图片解析必须以该 JSON 中的绝对路径为准。
- 若 `Glob` 返回 0 个文件但脚本能找到文件，以脚本结果为准；不得据此判断用户未初始化或未放文件。

## 代码知识库路径规则

默认代码知识库根路径为：

```text
.dev-standards/
```

常见子目录（存在则读取，不存在不强求齐全）：

```text
.dev-standards/knowledge/business/   # 业务规则/业务流程
.dev-standards/knowledge/codemap/    # 代码地图
.dev-standards/knowledge/service/    # 服务知识
.dev-standards/procdefs/             # 流程定义
```

定位顺序：

1. 先在当前 workspace / 项目根及其常见兄弟模块下查找 `.dev-standards/`（例如项目根、`*-common/.dev-standards/`）。
2. 若用户在本轮对话中已明确提供知识库路径，直接使用用户指定路径，不再重复询问。
3. 若默认路径不存在或为空：**立即停止定位读取**，明确提示用户：

> 当前项目未找到代码知识库（默认路径 `.dev-standards`）。  
> 是否有其他知识库目录？若有，请直接告诉 AI 知识库绝对/相对路径；若无，请确认是否仅基于需求文档与 `input/reference/` 接口文档继续。

4. 用户提供替代路径后，将该路径视为本次（及后续同版本）只读知识库根目录，并在阶段产物中写明实际使用路径。
5. 用户确认无知识库、仅基于需求/接口继续时，后续阶段按知识库缺失降级处理，并在产物中标注覆盖不完整风险。

## MCP 使用规则（可选，不强制；调不通必须 fail-open）

- **不强制要求读取/调用 MCP。** 无 MCP、MCP 不可用、调不通、超时、无工具、参数错误、或不想使用 MCP 时，可完全基于本地需求文档 + 代码知识库推进。
- **Fail-open 铁律（防止卡死，优先级高于一切 MCP 相关步骤）：**
  1. MCP 不是流程前置条件；任何阶段都不得因为“还没调通 MCP”而暂停、等待、轮询或反复重试。
  2. 同一会话内，每个 MCP 工具**最多尝试 1 次**。出现不可用/超时/报错/无返回/工具不存在/descriptor 读不到时：**立即停止该 MCP 调用**，记录原因，**马上回退本地文档继续**。
  3. **禁止**：同一工具连调多次、改参死磕、等待用户先修好 MCP、因 MCP 失败终止阶段0~4、把 MCP 失败写成阻断项。
  4. 调用 MCP 前若发现工具列表中无 `user-dev-standards` 相关工具，**直接跳过**，不要尝试调用。
  5. 读取 MCP descriptor/schema 失败时，视为 MCP 不可用，**直接跳过**，不要卡在“先读 schema”。
  6. MCP 成功与否都不影响进入下一动作：阶段0可做本地需求自检；阶段1以 `.dev-standards`/用户指定知识库为准；阶段2/3以需求+本地知识库+接口文档为准。
- 若环境中存在 `user-dev-standards` MCP **且**决定使用，调用前可读对应工具 descriptor/schema；读不到或调不通则按上面 fail-open 处理。
- 常用 MCP 工具（可选，全部可跳过）：
  - `get-business-rule`：阶段1辅助查询候选业务规则文档。建议先列表，再按关键词匹配。`projectPath` 禁止写死固定盘符路径，默认从当前 workspace 根目录自动推断。
  - `validate-requirement`：阶段0/阶段2前可选校验需求文档质量。
  - `get-service-knowledge`：阶段2/阶段3可选查询服务知识。
  - `query-standard`：仅在涉及代码评审、异常处理、事务、日志、数据库等规范风险时可选使用。
- 若本阶段**使用了 MCP**、尝试失败或主动跳过，建议在产物中写明；**未使用/调不通 MCP 都不是阻断项**：

```markdown
## MCP使用情况

- 未调用/失败/跳过原因：例如 MCP 不可用、调不通、超时、无匹配工具、本技能不强制 MCP，已 fail-open 回退本地需求文档与代码知识库。
- 处理：未重试、未等待修复；已继续当前阶段本地流程。
- 可选风险提示：未经过 MCP 交叉校验时，可能遗漏某些未写入本地知识库的补充规则。
```

## 输入输出约定

- 版本根目录：`.test-standards/<版本>/`，例如 `.test-standards/V1.12.0-xxx/`。
- 输入：`.test-standards/<版本>/input/prodword/`（需求文档，沿用原 requirement 逻辑）、`.test-standards/<版本>/input/prodword/prodword_pic/`（需求文档图片，尤其流程图）、`.test-standards/<版本>/input/reference/`（三方接口文档等联动文档）。
- 输出：`.test-standards/<版本>/output/` 下，按阶段写文件：`01-定位.md`、`02-变更分析.md`、`03-测试概要.md`、`04-测试用例.md`。
- 本地代码知识库（只读，默认）：`.dev-standards/knowledge/business/`、`.dev-standards/knowledge/codemap/`、`.dev-standards/knowledge/service/`、`.dev-standards/procdefs/`；若用户另行指定知识库根路径，则在该根路径下按同样相对结构查找。
- MCP知识源（可选）：`user-dev-standards` 下的业务规则、服务知识、需求校验、代码规范工具。
- 用例格式使用本技能内置的阶段4模板，固定字段为：`用例等级`、`所属模块`、`用例标题`、`前置条件`、`用例步骤`、`预期结果`。其中 `前置条件` 非必填；执行 `tc-gen` 时不需要额外读取 `.test-standards/templates/测试用例模板.md`。
- 各阶段细节参照同目录 `reference.md`：§ 一 Word转换命令、§ 二 状态迁移技巧、§ 三 接口测试补充清单、§ 五 操作偏离7类提问、§ 六 回归分析方法。

## 阶段进度清单

```markdown
- [ ] 阶段0 准备：Word 转 md + 读取输入 +（可选）需求质量自检/MCP校验
- [ ] 阶段1 定位：解析代码知识库路径 + 读取业务文档/codemap/procdefs（MCP 可选）
- [ ] 阶段2 变更分析：需求 vs 业务现状（服务知识/MCP 可选）
- [ ] 阶段3 测试概要：通过前置门禁后按6维度列测试点
- [ ] 阶段4 详细用例 + 回归清单
```

## 阶段0：准备（读取输入 + 可选需求校验）

1. 明确当前处理的 `<版本>`；若用户未给出版本，先询问，不要把产物写到 `.test-standards` 根目录。
2. 使用 `tc-gen/scripts/list_version_inputs_utf8.py` 列出 `.test-standards/<版本>/input/prodword/`、`.test-standards/<版本>/input/prodword/prodword_pic/` 和 `.test-standards/<版本>/input/reference/` 下的所有文件；Windows/中文路径场景禁止用 `Glob` 的空结果作为缺文件结论。
3. 对每个 `.docx` / `.doc` 转换为同名 `.md` 放回 `input/prodword/`（保留原文件），并同步抽取 Word 内图片到 `input/prodword/prodword_pic/`。转换后的 md 中图片引用应尽量指向 `prodword_pic/` 下的文件；无法自动建立引用时，必须在 md 附近标注 `[图片：prodword_pic/<文件名>，需人工/AI查看]`。转换命令参照 `reference.md` § 一。
4. 读取需求文档 + 全部联动文档 + `prodword_pic/` 下图片。三方接口文档特别留意：接口入参/出参/异常码/超时/重试/幂等。
5. 解析需求 md 时，搜索“流程图”“业务流程”“流程”“时序图”“泳道图”“状态流转”“节点”“步骤”等字眼，定位其附近图片引用；对这些图片必须重点查看并提炼流程节点、角色、分支、状态迁移、接口调用顺序和异常路径。图片内容与正文冲突时，单独列为疑点。
6. **（可选）** 若 MCP 可用，可调用 `validate-requirement` 校验需求质量；未调用 MCP 时，由 agent 基于需求文档做可测试性/闭环/边界自检即可，**不因未调用 MCP 而阻断**。
7. 输出「读到的文档、图片/流程图清单、需求核心、需求校验结论（自检或 MCP）、待确认疑点」，停下来确认。

阶段0产物/回复必须包含：

- 输入文件清单。
- 图片清单：`prodword_pic/` 下图片总数、已重点解析的流程图/疑似流程图、未能解析的图片。
- 需求核心摘要。
- 流程图解析摘要：从图片提取出的主流程、角色、节点、分支和状态流转。
- 需求校验：错误/警告/建议（来源标注自检或 MCP；未做 MCP 不影响继续）。
- 测试范围待确认项，例如是否覆盖个人CA、存量数据、签章异常、静默签章、接口字段级。

## 阶段1：定位（代码知识库匹配业务流程）

1. **先解析代码知识库路径**（见「代码知识库路径规则」）：
   - 默认查找 `.dev-standards/`；
   - 找不到则提示用户：当前项目没有代码知识库，是否有其他知识库目录？有则请用户告知路径；无则请用户确认是否仅基于需求/接口继续；
   - **在用户回复前不得擅自用活源码替代，也不得跳过询问继续“假装已定位”。**
2. **（可选）** 若 MCP 可用，可调用 `get-business-rule` 辅助列出/匹配业务规则；未调用不阻断。
3. 根据需求内容和（可选）MCP 候选，在知识库 `knowledge/business/` 下匹配对应业务流程文档。
4. 读取匹配到的本地业务文档全文 + 对应 `codemap` 代码地图 + 必要的 `procdefs` 流程定义。
5. 输出到 `.test-standards/<版本>/output/01-定位.md`：
   - 实际使用的知识库根路径。
   - （若使用）MCP 查询关键词、命中文档、排除文档及理由；未使用 MCP 则注明“未使用 MCP”。
   - 受影响流程、关键章节、状态/配置/通知矩阵。
   - 可能涉及的节点/Handler/服务。
   - 需求与哪些既有功能相关。
6. 停下来确认定位是否准确。

### ⛔ 知识库不存在时的强制停止与询问规则

当默认 `.dev-standards/`（及已尝试的常见位置）不存在或为空时，**必须立即停止阶段1**，在对话中明确询问用户，并在 `01-定位.md` 写明原因：

```markdown
## 阶段1定位结果

- 默认代码知识库路径：`.dev-standards/`（未找到或为空）
- MCP：未强制使用；本次未调用 / 或已调用但无有效结果（按实填写）
- 结论：当前项目没有可用的默认代码知识库，已停止。请用户确认：
  1. 是否有其他知识库目录？若有，请提供路径；
  2. 若无，是否仅基于需求文档和 `input/reference/` 接口文档继续进入阶段2（将按知识库缺失降级，回归覆盖可能不完整）。
```

用户回复后：

- **提供了其他知识库路径**：将该路径记为本次知识库根，继续完成阶段1读取与定位。
- **确认无知识库、仅基于需求/接口继续**：在 `01-定位.md` 标注降级，阶段2起主要对照需求与接口文档；阶段3门禁中与 knowledge/codemap 相关项改为“已确认缺失并降级”。
- **用户暂不回复**：保持停止，不得自行读取活源码继续。

## 阶段4：详细用例 + 回归清单

> 铁律：一条用例 = 单路径 + 单组数据 + 单个明确预期。严禁 1 个测试点对 1 条用例，严禁一条用例里塞多个校验点。

### 用例裂变规则

- 正反例：正向路径 1 条 + 每一条失败/异常路径各 1 条。
- 等价类：每个关键输入字段，有效值 / 各类无效值 各成一条。
- 边界值：每个关键数值/长度字段，上界、下界、越界各一条（字段长度、金额、日期、数量）。
- 枚举逐值：枚举类输入每个取值至少一条。
- 条件必填：触发条件满足时 1 条 + 不满足时 1 条；不仅限于接口字段，业务逻辑条件必填同样适用（例：法人证件=身份证 → 报四要素；≠ 身份证 → 报二要素）。
- 接口字段级：每字段按必填缺失 / 类型格式错 / 枚举越界 / 条件必填触发拆分；一条只破坏一个字段。
- 多步骤流程：每个独立校验点、每次接口调用、每个 UI 规则各成一条。

**裂变反例与正解**（一条塞多个校验是最常见错误）：

> ❌ 反例：appId空、sign空、custType错、subjectType错 → 预期失败（一条塞了4个校验点）
>
> ✅ 正解：裂成4条，各自单一预期：
> - appId 缺失 → 接口拒绝并提示 appId 必填
> - sign 缺失 → 接口拒绝并提示验签失败
> - custType=PERSON（企业场景）→ 拒绝/类型不符
> - subjectType 与核验对象不符 → 拒绝

**裂变比快速自检**：用例总数低于测试点数 × 2 时需自查是否遗漏裂变；允许基于高风险判断标准对低风险同质场景合并，但须写入合并说明清单；接近 1:1 且无合并说明的，视为未裂变，返工。

**维度专项裂变铁律（不得跳过）**

> **高风险判断标准（以下任一条件满足即为高风险，不得合并）：**
> - 涉及资金计算、金额口径、资金划转或账务落库
> - 接口返回的错误码/状态码有明确的系统处理逻辑（非静默忽略）
> - 需求文档或接口文档中明确标注"必须"、"禁止"、"固定值"、"强制"等字样
> - 状态流转的终态（如成功、失败、余额不足）或不可逆操作
> - 与监管合规、签约协议、KYB/实名认证直接相关的场景
>
> 不满足上述任一条件，且多个场景走同一代码分支、验证同一规则时，可判定为低风险同质场景，允许合并，但必须写入合并说明清单。

- **判定表裂变（维度2）**：阶段3输出的每张判定表，高风险/高频/强监管条件组合应逐行覆盖；低风险且同质组合可按等价类合并，但必须在合并说明清单中写明合并依据与剩余风险。阶段3预算值用于预警，不作为机械下限。
- **偏离矩阵裂变（维度4）**：阶段3中「步骤 × 偏离类别」矩阵应优先覆盖高风险步骤与关键偏离类别；允许对重复、低风险且同质的单元格合并验证，但需在合并说明清单中注明被合并单元格、合并依据和补偿性回归策略。阶段3预算值用于预警，不作为机械下限。

  **各类操作偏离的裂变方法（逐类展开，不得只写一条"操作异常"笼统覆盖）**：

  | 类别 | 裂变方法 | 必带断言 |
  |---|---|---|
  | 1. 前置/必填未满足 | 每个前置操作/必填项未满足各成一条 | 系统阻止推进或给出明确提示；不生成脏数据 |
  | 2. 数量与上限 | 传0个（下限）/ 传最大值 / 传最大值+1（越界）各成一条 | 各边界的系统响应符合规则；不超限通过、超限拦截 |
  | 3. 增删改+重做（**核心**） | 增 / 删 / 改 / 删后重加 / 改后再改 各成一条 | **最终落库内容、数量与最后一次操作一致，不残留旧数据** |
  | 4. 操作顺序/路径偏离 | 每个乱序/跳步/返回重进/切换互斥选项（如线上↔线下）场景各成一条 | 已填数据保留 or 清空符合产品定义；互斥切换后旧数据正确清理 |
  | 5. 重复/多次提交 | 重复提交各成一条 | 不产生重复数据/记录；幂等保护生效 |
  | 6. 取消/中断/重入 | 中断后重入各成一条（草稿续填 / 清空 分别成一条） | 草稿保留 or 清空符合产品定义；重入后数据状态与预期一致 |

  > 类别7（取值边界）不在此矩阵裂变，由通用裂变规则（等价类/边界值/枚举逐值/条件必填）独立展开。
- **接口与数据边界全量裂变（维度5）**，当前项目以 Dubbo 调用为主，除响应与错误处理外，必须重点覆盖“请求参数传参逻辑”。以下五类必须逐项展开，不得遗漏：
  1. **错误码逐值**：三方接口文档中每个有处理逻辑的业务错误码（排除标注"不存在"的）各成一条，用例步骤触发该错误码，预期结果写明系统响应行为（自动重试/前端提示/进异常台账/人工介入等）。
  2. **请求参数传参逻辑逐规则**（Dubbo 重点）：接口文档备注或需求文档中定义的关键传参规则（固定值、条件必填、字段映射、默认值、互斥/依赖关系、枚举取值、是否透传）应逐条成用例；每条用例仅校验一条规则，断言实际发起的 Dubbo 请求参数与规则一致。
  3. **响应字段落库逐字段**：接口文档中标注"保存"或需落库的每个响应字段，各成一条用例，断言该字段值正确落库（值来源正确、格式正确、不为空），并且页面相关的响应是正确的。
  4. **业务通知/邮件要素逐条**：需求文档中提及的每条告警邮件/系统通知，必须按「标题、收件人、正文关键字段、附件（如有）」各成一条独立用例；通知类的用例不得以一条"验证邮件发送成功"笼统覆盖。

> **补充检查**：以上4类覆盖了 Dubbo 请求/响应/通知的主链路；同时参照 `reference.md` § 三，对**超时、重试/幂等、签名/证书、联动一致性**（三方返回后本侧多系统状态同步）逐项自查，这4项无专门子类对应但不可遗漏。

   ```markdown
   | # | 被合并/裁剪项 | 所属维度 | 合并/裁剪原因 | 剩余风险 | 补偿策略 |
   |---|---|---|---|---|---|
   | 1 | 示例：判定表1第3行+第4行 | 维度2 | 两行触发条件相同，仅企业类型不同，系统走同一分支逻辑 | 极低，同一代码路径 | 回归时覆盖其中一行即可 |
   ```

   若本次无任何合并/裁剪，必须明确写"本次无合并/裁剪项"，不得留空或省略该节。

9. **自检（禁止跳过，逐项核查后方可提交）**：

   | # | 自检项 | 检查方法 | 通过标准 |
   |---|---|---|---|
   | ① | 维度2判定表覆盖充分性 | 核对高风险/高频/强监管组合是否逐行覆盖；低风险合并是否有依据 | 高风险组合100%覆盖，合并项可追溯且剩余风险可接受 |
   | ② | 维度4偏离矩阵覆盖充分性 | 核对关键步骤与关键偏离类别覆盖；检查合并单元格说明 | 关键步骤与关键偏离类别100%覆盖，合并说明完整 |
   | ③ | 维度5-错误码覆盖 | 列出接口文档所有有效业务错误码，逐一确认已各成独立用例 | 所有有效错误码均有对应用例 |
   | ④ | 维度5-请求参数传参逻辑覆盖（Dubbo） | 列出接口文档备注/需求文档中的关键传参规则（固定值、条件必填、映射、默认值、互斥/依赖等），逐一确认对应校验用例 | 关键传参规则100%有对应用例，且每条规则可追溯到文档来源 |
   | ⑤ | 维度5-落库字段覆盖 | 列出接口文档标注"保存"的响应字段，逐一确认已各成落库验证用例 | 所有需落库字段均有对应用例 |
   | ⑥ | 维度5-通知/邮件要素覆盖 | 列出需求文档中所有通知/邮件场景，确认已按要素（标题/收件人/正文字段/附件）各成用例 | 无通知场景被笼统覆盖 |
   | ⑦ | 总体覆盖与成本平衡 | 对照阶段3预算参考量，评估是否存在明显漏测；说明裁剪/合并原因 | 不存在关键漏测，覆盖结论可被复核，成本与收益匹配 |

   结果处置按风险分级执行：高风险项（核心链路/资金口径/强监管/生产高频）未通过时必须返工补齐；中低风险项未通过时，可在产物中登记「未覆盖项、原因、影响评估、补偿性回归计划、预计补齐时间」，并经用户确认后继续输出。

### 内置用例模板

阶段4生成 `04-测试用例.md` 时，直接使用以下模板：

```markdown
# 测试用例 - <版本>

> 需求来源：`.test-standards/<版本>/input/prodword/`  
> 参考资料：`.test-standards/<版本>/input/reference/`  
> 输出位置：`.test-standards/<版本>/output/04-测试用例.md`

## 表格规范

必填字段：

- `用例等级`：只允许 `1`、`2`、`3`、`4`。
- `所属模块`：支持按 `/` 分层级，后续转 XMind 使用。例如 `建档/自主建档/线上授权书`。
- `用例标题`：单条原子用例标题，标题应能独立表达校验目标。
- `用例步骤`：单路径、单组数据、单个明确动作链；多步用 `<br>` 或 `1. 2. 3.` 分隔。
- `预期结果`：唯一明确预期，必须可断言。

非必填字段：

- `前置条件`：如有，转成 XMind 后作为备注放到用例标题节点下。

## 用例表

| 用例等级 | 所属模块 | 用例标题 | 前置条件 | 用例步骤 | 预期结果 |
|---|---|---|---|---|---|
| 1 | 一级模块/二级模块 | 示例：线上授权书未完成倒计时不允许下一步 | 已进入线上授权书预览页 | 1. 打开授权书预览页<br>2. 倒计时未结束时点击【下一步】 | 【下一步】不可点击或提示需完成阅读；不生成阅读日志；不进入后续报数 |

## 填写要求

- 一条用例只覆盖一个明确校验点，禁止一条用例塞多个异常字段或多个分支。
- `所属模块` 必须能形成 XMind 层级，不要为空。
- `用例标题` 中不要手写等级，转 XMind 脚本会自动把等级标到标题上。
- `用例步骤` 和 `预期结果` 内如需换行，优先使用 `<br>`。
```

### 转 XMind

阶段4完成后，可用脚本把 `.test-standards/<版本>/output/04-测试用例.md` 转成 XMind：

```bash
python "<当前软件skills目录>/tc-convert/scripts/cases_to_xmind.py" ".test-standards/<版本>"
```

也可以显式指定输入和输出：

```bash
python "<当前软件skills目录>/tc-convert/scripts/cases_to_xmind.py" ".test-standards/<版本>/output/04-测试用例.md" ".test-standards/<版本>/output/<版本>.xmind"
```

XMind 层级规则：

- 根节点：版本目录名称，例如 `V1.12.0-xxx`。
- 中间节点：`所属模块` 按 `/` 拆分形成层级。
- 用例节点：`用例标题`，脚本自动加等级前缀，如 `【等级1】xxx`。
- 用例节点下包含：`用例步骤`、`预期结果`。
- `前置条件` 如有，写入用例节点备注。

## 注意事项

- 全程中文。术语与业务文档保持一致。
- 知识库与代码只读，不修改 `.dev-standards`（或用户指定的知识库目录）和业务源码。
- **不强制 MCP；MCP 调不通必须 fail-open，禁止重试卡死。** 若使用了 MCP，其结果只是辅助证据，不是最终真相；须和本地文档、代码地图、用户确认结论交叉校验。
- 若业务文档、需求、（若有）MCP结果出现矛盾，明确指出并提示用户确认。
- 阶段产物要写清楚来源，避免“AI拍脑袋”的测试点。
- 需求文档图片可能包含版本迭代流程图。阶段0必须抽取并读取，阶段3必须把流程图中的角色、节点、分支、状态流转和接口调用顺序纳入测试概要设计。
- **代码知识库默认路径为 `.dev-standards`。** 找不到时必须询问用户是否有其他知识库目录；有则按用户路径继续，无则在用户确认后按需求/接口降级继续。
- **不得以活源码替代任何知识库文档**。`codemap`、`business`、`procdefs` 均指代码知识库下的**静态文档**。当这些文档不存在且用户尚未确认处理方式时，必须停下来询问，绝不自行读取 `.java`/`.xml`/`.yml` 等活源码作为替代。
